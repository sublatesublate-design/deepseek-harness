# Agent Note: 基于 Web profile 的原生桌面外壳

Status: implemented

[English](2026-08-14-native-desktop-shell.md) | 中文

## 问题

浏览器应用已经持有完整的用户工作流，但从终端启动后，窗口生命周期、聚焦、桌面框架和外部链接行为都交给了通用浏览器。桌面应用需要原生窗口行为，同时不能创建另一套可能偏离插件组合 Web profile 的渲染器。

## 决策

**桌面应用包装已发布的 Web profile。** `apps/desktop` 将工作区 CLI 解析为应用依赖，通过 Electron 内置 Node 模式在桌面专用的 3081 端口启动回环 `dsh web` 进程，然后在单个 Electron `BrowserWindow` 中加载。这条进程路径同时适用于 Windows 与 macOS，无需按平台选择 `node.exe` 或 `node`。托管默认值与浏览器命令的 3080 端口分离，防止意外复用另一个已安装版本。`DSH_DESKTOP_URL` 选择显式管理的本地开发服务，`DSH_DESKTOP_PORT` 更改托管端口。

**托管 API 要求每进程随机凭据。** 桌面进程生成 256 位随机数，通过 `DSH_CONTROL_TOKEN` 将令牌传给 Host，并把 `x-dsh-control-token` 注入窗口的 HTTP 请求与 WebSocket 握手。令牌不会进入渲染器 URL 或应用启动数据，其凭据形环境变量名会被共享清理器从 agent 子进程环境中移除。就绪探测要求 `/api/auth-probe` 在携带凭据时成功、匿名时返回 401，因此不会接管已占用 3081 的未认证进程。未配置令牌的普通 `dsh web` 保持兼容；显式 `DSH_DESKTOP_URL` 可与 `DSH_DESKTOP_CONTROL_TOKEN` 配对。

**Web 渲染器通过 URL 状态选择桌面框架。** Electron 窗口加载 `?desktop=1&platform=<platform>`。仅在该模式下，Web 入口挂载一个固定拖动区域，并按其高度缩减应用根节点。普通浏览器 URL 保持既有的全高布局与 DOM。

**原生进程持有原生策略。** 渲染器使用上下文隔离和 Chromium 沙箱，禁用 Node integration。新窗口在操作系统浏览器中打开，页面权限请求被拒绝，一个进程持有应用实例，常规窗口尺寸保存在 Electron 的用户数据目录中。Windows 使用稳定的应用 ID 与标题栏 overlay；macOS 使用内嵌红黄绿按钮、标准应用菜单、Dock 激活行为与 Dock 图标。

**启动故障留在原生窗口内。** Host 就绪等待开始前窗口已经存在。启动失败会渲染一份经过转义的本地恢复文档，展示故障摘要、长度受限的最近输出、持久日志路径，以及重试自有服务或在文件管理器中显示日志的操作。重试会短暂等待旧的自有进程退出，再重新绑定。

**源码启动器只持有其创建的进程。** 桌面进程创建的服务在应用退出时，于 Windows 终止其进程树，在其他平台发送 `SIGTERM`。显式配置的开发 URL 仍由外部持有。

## 曾考虑的替代方案

**构建第二套 React 桌面渲染器。** 不采用：会话、设置、工具、审批、工作区和插件提供的 UI 都需要重复集成，并可能偏离浏览器行为。

**通过 `file://` 加载 Web 构建产物。** 不采用：浏览器应用依赖 Host API 和运行时注入的启动清单，只有静态文件无法提供可用的 Harness 会话。

**要求用户手动启动 `dsh web`。** 不采用：原生启动器应持有可用的冷启动路径。显式开发 URL 仍可保留，而无需削弱经认证的托管默认值。

**信任回环地址上的所有进程。** 不采用：模型控制的 shell 或无关的同用户进程可以直接调用 Host API。每进程随机认证使“持有桌面凭据”与“网络可达”成为两件不同的事。

**允许 Electron 渲染器访问 Node.js。** 不采用：页面已经通过仅限回环的 Host API 访问特权操作。Node integration 会建立第二条更宽的权限路径。

## 后果

桌面应用与浏览器应用共用同一套产品实现，Electron 增加平台感知的原生框架、窗口尺寸记忆、单实例聚焦、受控外部导航、经认证的本地控制面和可操作的启动恢复。源码启动器可在 Windows 与 macOS 上从已构建的仓库运行，Node.js 工具链只用于安装和构建。产品引导、自动更新、签名和可分发安装包属于后续独立的发布工作。
